PROJECT DAY · SIX PHASE GUIDE

Project Day 상세 실습과제 가이드

Markdown 기획서 기반 웹사이트 구축 과정을 실제 프로젝트처럼 진행하기 위한 안내서입니다. 각 페이즈에서 “무엇을 하는지”, “왜 필요한지”, “어떤 결과물을 남겨야 하는지”를 확인하고 완료 기준을 충족한 뒤 다음 단계로 이동하세요.

1. 아이디어2. 기획 문서3. 구현 4. 테스트5. 변경 개선6. 회고 발표

기존 Task 과제 명세

기존 Task의 요구사항은 변경하지 않았습니다. 아래 Task를 기본 과제로 수행하고, 이어지는 6개 페이즈 상세 가이드를 이용해 결과물의 품질과 프로젝트 진행 과정을 보완하세요.

Task 01. 아이디어 구체화 및 세 문장 정의 (Phase 1)

Codex에게 전달할 프로젝트의 목적과 사용자 역할을 다음 세 문장 양식으로 작성합니다.

1. 사이트 목적: 학생이 자신의 카드를 선택하여 QR 코드로 출석하고, 선생님이 실시간으로 확인하는 시스템이다.
2. 학생 역할: 이름 검색 ➔ ID 카드 클릭 ➔ 모바일 QR 스캔 ➔ 출석 버튼 클릭
3. 선생님 역할: 전체 출석 현황 모니터링 대시보드 ➔ 실시간 갱신 확인 ➔ 출석/미출석 필터링

Task 02. 5대 Markdown 기획 문서 팩 작성 (Phase 2)

Codex에 다음 5개 파일 생성을 요청하고 완료 기준을 검토합니다.

  • SITE_SPEC.md: 화면 구성, 기능, 디자인, 완료 검수 기준
  • USER_FLOWS.md: 사용자별 단계별 동선
  • DATA_MODEL.md: 학생 및 출석 데이터 모델
  • IMPLEMENTATION_PLAN.md: 구현 순서
  • CONVERSATION.md: 대화 기록

Task 03. 코덱스 코드 생성 및 테스트 (Phase 3 & 4)

Codex에 기획서를 읽게 한 후 website/ 폴더 생성을 요청합니다.

프롬프트: "작성된 기획서 문서를 먼저 읽고, website/ 폴더 아래 학생 출석 QR 페이지와 선생님 모니터링 페이지를 완성해 줘."

Task 04. 요구사항 변경 및 발표 준비 (Phase 5 & 6)

기획 문서를 먼저 수정한 후 코드를 개정하고, 대화 이력을 CONVERSATION.md에 정리하여 발표를 진행합니다.

6개 페이즈 상세 프로젝트 가이드

PHASE 1 · DISCOVER

아이디어 구체화: 만들기 전에 문제를 정의하는 단계

화면과 기능을 떠올리기 전에 누구의 어떤 불편을 해결할지, 이번 프로젝트에서 어디까지 만들지를 팀이 합의하는 페이즈입니다.

이 페이즈에서 하는 일

사용자 인터뷰를 가정해 문제, 사용자, 사용 상황, 핵심 행동과 성공 조건을 좁힙니다.

필수 결과물

PROJECT_BRIEF.md3문장 정의범위표성공 지표

가장 중요한 기준

팀원과 Codex가 같은 사용자를 상상하고 “무엇을 만들지 않는지”까지 설명할 수 있어야 합니다.

학생 수행 순서

  1. 문제를 관찰합니다. 출석 확인에서 학생과 선생님이 겪는 불편을 각각 3개씩 적습니다.
  2. 핵심 사용자를 선택합니다. 모든 사용자를 만족시키려 하지 말고 학생·선생님 중 각자의 가장 중요한 목표를 한 문장으로 정합니다.
  3. 핵심 행동을 연결합니다. 수업 입장부터 출석 완료 확인까지 시작-행동-결과 흐름을 작성합니다.
  4. 범위를 나눕니다. 필수(Must), 가능하면(Should), 이번에는 제외(Out)로 기능을 분류합니다.
  5. 성공 조건을 수치화합니다. 예: 학생이 30초 안에 출석하고 선생님이 미출석자를 10초 안에 찾을 수 있다.

실제 프로젝트에서 고려할 것

  • QR을 친구에게 전달하는 대리 출석과 중복 출석을 어떻게 다룰지 결정합니다.
  • 이름, 학번, 위치, IP 같은 개인정보는 꼭 필요한 항목만 수집하고 목적과 보관 기간을 정합니다.
  • 인터넷 불안정, 카메라 권한 거부, 동명이인처럼 이상적인 흐름 밖의 상황을 미리 적습니다.
  • 하루 안에 만들 수 있는 규모인지 시간과 팀 역량을 기준으로 범위를 줄입니다.

완료 체크

  • 사용자, 문제, 핵심 행동이 각각 한 문장으로 명확하다.
  • 필수 기능과 제외 기능이 구분되어 있다.
  • 성공 여부를 확인할 지표가 최소 2개 있다.
  • 팀원 전원이 같은 3문장 정의에 동의했다.

Codex 활용 포인트

우리 팀의 출석 서비스 아이디어를 비판적으로 검토해 줘. 바로 기능을 추가하지 말고 ① 모호한 표현 ② 확인되지 않은 가정 ③ 가장 위험한 예외 상황 ④ 하루 프로젝트에서 제외해야 할 범위를 질문 형태로 제시해 줘. 답변 후 합의된 내용만 PROJECT_BRIEF.md 구조로 정리해 줘.
PHASE 2 · DEFINE

기획 문서화: 생각을 구현 가능한 약속으로 바꾸는 단계

아이디어를 화면, 사용자 흐름, 데이터, 구현 순서와 완료 기준으로 나누어 팀과 Codex가 함께 사용할 단일 기준을 만듭니다.

이 페이즈에서 하는 일

5개 Markdown 문서가 서로 연결되도록 요구사항 ID, 흐름, 데이터 필드와 테스트 기준을 구체화합니다.

필수 결과물

SITE_SPEC.mdUSER_FLOWS.mdDATA_MODEL.mdIMPLEMENTATION_PLAN.mdCONVERSATION.md

가장 중요한 기준

“좋게”, “빠르게”, “실시간” 같은 표현 대신 누가 보아도 확인 가능한 완료 기준을 사용합니다.

학생 수행 순서

  1. SITE_SPEC을 작성합니다. 화면 목록, 기능 요구사항 ID, 디자인 원칙, 반응형 조건과 완료 기준을 적습니다.
  2. USER_FLOWS를 작성합니다. 학생·선생님의 정상 흐름과 QR 만료, 중복 출석, 검색 결과 없음 등 예외 흐름을 분리합니다.
  3. DATA_MODEL을 작성합니다. Student, ClassSession, Attendance의 필드, 타입, 필수 여부, 관계와 상태값을 정의합니다.
  4. IMPLEMENTATION_PLAN을 작성합니다. 기반 화면 → 데이터 → 핵심 기능 → 예외 처리 → 테스트 순으로 작은 작업을 나눕니다.
  5. 문서 간 모순을 검사합니다. 화면의 기능이 흐름과 데이터에 모두 존재하는지 요구사항 추적표로 확인합니다.

실제 프로젝트에서 고려할 것

  • UI에 보이는 “출석 완료”와 실제 저장된 Attendance 상태가 일치해야 합니다.
  • 학생 이름을 고유키로 사용하지 말고 별도 studentId를 둡니다.
  • 날짜·시간대, 지각 기준, QR 만료 시각, 선생님의 수동 수정 권한을 명시합니다.
  • 문서마다 같은 개념에 다른 이름을 사용하지 않도록 용어집을 만듭니다.

완료 체크

  • 모든 핵심 기능에 요구사항 ID와 수용 기준이 있다.
  • 정상 흐름과 3개 이상의 예외 흐름이 있다.
  • 데이터 필드의 타입·필수 여부·관계가 정의됐다.
  • 구현 순서와 각 작업의 완료 조건이 명확하다.

Codex 활용 포인트

PROJECT_BRIEF.md를 기준으로 5개 기획 문서를 작성해 줘. 먼저 필요한 확인 질문을 하고, 답변되지 않은 내용은 [미결정]으로 표시해 줘. 각 기능에는 FR-001 형식의 ID와 Given-When-Then 수용 기준을 붙이고, 다섯 문서 사이의 모순과 누락을 마지막에 별도 표로 검토해 줘.
PHASE 3 · BUILD

Codex 기반 구현: 문서를 작동하는 제품으로 옮기는 단계

Codex가 임의로 제품을 결정하게 하지 않고, 기획 문서를 기준으로 작업 계획과 변경 범위를 검토하며 작은 단위로 구현합니다.

이 페이즈에서 하는 일

프로젝트 구조를 만들고 학생 출석 화면과 선생님 대시보드를 우선순위에 따라 구현합니다.

필수 결과물

website/README.md실행 화면구현 로그

가장 중요한 기준

코드가 많아지는 것보다 기획서의 수용 기준이 실제로 동작하고 다른 사람이 실행할 수 있어야 합니다.

학생 수행 순서

  1. Codex에 문서를 먼저 읽힙니다. 이해한 요구사항, 미결정 사항, 구현 순서를 요약하게 하고 팀이 승인합니다.
  2. 실행 환경을 고정합니다. 기술 스택, 폴더 구조, 실행 명령, 지원 브라우저와 데이터 저장 방식을 README에 적습니다.
  3. 핵심 흐름부터 만듭니다. 학생 선택 → QR 확인 → 출석 저장 → 선생님 현황 반영의 세로 흐름을 먼저 완성합니다.
  4. 작은 변경마다 실행합니다. 한 기능을 구현할 때마다 브라우저와 콘솔을 확인하고 다음 작업으로 넘어갑니다.
  5. 문서와 구현을 대조합니다. 요구사항 ID별 구현 위치와 확인 방법을 IMPLEMENTATION_PLAN에 표시합니다.

실제 프로젝트에서 고려할 것

  • API 키와 비밀번호를 코드에 직접 넣거나 저장소에 올리지 않습니다.
  • 새 라이브러리를 추가하기 전에 꼭 필요한지, 팀원이 같은 환경에서 설치할 수 있는지 확인합니다.
  • AI가 기존 파일을 크게 바꾸려 할 때는 변경 diff와 영향 범위를 먼저 검토합니다.
  • 데모용 임시 데이터와 실제 저장 데이터를 명확히 구분합니다.
  • 모바일 QR 화면은 터치 영역, 로딩, 카메라 권한 거부를 고려합니다.

완료 체크

  • README의 명령만으로 다른 팀원이 실행할 수 있다.
  • 학생·선생님 핵심 흐름이 연결되어 동작한다.
  • 브라우저 콘솔에 해결되지 않은 오류가 없다.
  • 기획서에 없는 기능을 임의로 추가하지 않았다.

Codex 활용 포인트

5개 기획 문서를 먼저 읽고 요구사항 ID, 미결정 사항, 구현 순서를 요약해 줘. 아직 코드를 작성하지 말고 생성·수정할 파일과 이유를 제안해 줘. 내가 계획을 확인한 뒤 website/ 아래에 가장 작은 실행 단위부터 구현하고, 각 단계마다 실행 방법과 확인할 수용 기준을 알려 줘.
PHASE 4 · VERIFY

기능 및 시나리오 테스트: “되는 것 같다”를 증거로 바꾸는 단계

정상 사용뿐 아니라 실수, 중복, 만료, 권한 거부와 화면 크기 변화에서도 제품이 예측 가능하게 동작하는지 확인합니다.

이 페이즈에서 하는 일

요구사항별 테스트 시나리오를 실행하고 실제 결과, 증거, 결함과 재검증 결과를 기록합니다.

필수 결과물

TEST_PLAN.md테스트 결과표오류 캡처BUG_LOG.md

가장 중요한 기준

테스트 통과 개수보다 실패가 재현되고 수정 후 다시 검증되었는지가 중요합니다.

학생 수행 순서

  1. 수용 기준을 테스트로 변환합니다. 사전 조건, 행동, 기대 결과, 실제 결과, 증거 항목을 만듭니다.
  2. 정상 시나리오를 확인합니다. 학생 출석과 선생님 현황 반영의 전체 흐름을 처음부터 끝까지 실행합니다.
  3. 예외 시나리오를 실행합니다. 빈 검색, 동명이인, 중복 클릭, 만료 QR, 네트워크 실패, 권한 거부를 시험합니다.
  4. 다양한 환경을 확인합니다. 모바일·태블릿·데스크톱, 키보드 조작, 긴 이름과 많은 학생 데이터를 점검합니다.
  5. 결함을 수정하고 회귀 테스트합니다. 원인과 수정 내용을 기록하고 관련된 기존 기능까지 다시 실행합니다.

최소 테스트 시나리오

  • 정상 출석 후 대시보드 인원과 학생 상태가 즉시 일치한다.
  • 같은 학생이 두 번 제출해도 한 건만 유효 처리된다.
  • 만료된 QR과 잘못된 수업 QR은 이유와 함께 거절된다.
  • 검색 결과가 없거나 동명이인일 때 잘못된 학생을 선택하지 않는다.
  • 저장 실패 시 성공 메시지를 보여 주지 않고 재시도 방법을 안내한다.
  • 375px 모바일 화면에서 가로 스크롤 없이 핵심 기능을 사용할 수 있다.

완료 체크

  • 각 요구사항 ID에 테스트 결과가 연결되어 있다.
  • 정상·예외·반응형·접근성 테스트를 수행했다.
  • 실패 항목에는 재현 절차와 증거가 있다.
  • 수정한 결함을 다시 테스트해 통과를 확인했다.

Codex 활용 포인트

기획 문서의 수용 기준을 바탕으로 테스트 표를 만들어 줘. 정상 경로만 작성하지 말고 중복 출석, 만료 QR, 동명이인, 네트워크 오류, 모바일 레이아웃, 키보드 접근 시나리오를 포함해 줘. 각 테스트에 사전 조건, 수행 단계, 기대 결과, 증거 방법을 작성하고 아직 실행하지 않은 항목은 PASS로 표시하지 마.
PHASE 5 · ITERATE

사이트·문서 연쇄 개선: 변경을 안전하게 반영하는 단계

새 요구사항을 코드에 바로 넣지 않고 명세, 사용자 흐름, 데이터, 테스트에 미치는 영향을 먼저 확인한 뒤 구현합니다.

이 페이즈에서 하는 일

변경 요청을 분석해 기획 문서를 먼저 갱신하고 최소 코드 변경과 회귀 테스트로 개선합니다.

필수 결과물

CHANGE_REQUEST.md영향 분석표문서 diff코드 diff회귀 결과

가장 중요한 기준

새 기능을 추가한 뒤에도 문서와 코드가 같은 제품을 설명하고 기존 핵심 흐름이 유지되어야 합니다.

학생 수행 순서

  1. 변경 요청을 한 문장으로 재작성합니다. 요청자, 이유, 기대 결과와 완료 기준을 확인합니다.
  2. 영향 범위를 분석합니다. 화면, 흐름, 데이터 모델, 권한, 테스트, 일정에 미치는 영향을 표로 만듭니다.
  3. 문서를 먼저 수정합니다. 관련 요구사항 ID와 버전을 갱신하고 변경 전·후 차이를 팀이 승인합니다.
  4. 최소 범위로 구현합니다. Codex에게 수정 대상 파일과 예상 diff를 먼저 보여 달라고 한 뒤 코드를 변경합니다.
  5. 회귀 테스트합니다. 새 수용 기준과 영향을 받는 기존 시나리오를 모두 재검증합니다.

실제 프로젝트에서 고려할 것

  • “실시간 현황” 추가가 새로고침, polling, WebSocket 중 어떤 의미인지 합의합니다.
  • 데이터 필드 변경 시 기존 데이터와 화면이 깨지지 않는지 마이그레이션을 생각합니다.
  • 요청 하나 때문에 전체 코드를 다시 만드는 것보다 작은 diff를 우선합니다.
  • 변경 요청이 프로젝트 시간과 목표를 벗어나면 구현 대신 다음 버전 백로그로 보냅니다.
  • 요청자의 말과 실제 사용자 가치가 충돌하면 질문하고 결정 근거를 남깁니다.

완료 체크

  • 변경 이유와 완료 기준이 문서화됐다.
  • 영향받는 문서와 코드 파일을 설명할 수 있다.
  • 문서 변경이 코드 변경보다 먼저 승인됐다.
  • 새 테스트와 관련 회귀 테스트가 모두 기록됐다.

Codex 활용 포인트

변경 요청을 바로 구현하지 말고 SITE_SPEC, USER_FLOWS, DATA_MODEL, IMPLEMENTATION_PLAN, 기존 테스트에 미치는 영향을 분석해 줘. 수정이 필요한 문서 항목과 코드 파일, 기존 기능이 깨질 위험, 추가할 회귀 테스트를 표로 보여 줘. 내가 승인한 뒤 문서를 먼저 수정하고 최소 diff로 구현해 줘.
PHASE 6 · SHARE

작업 이력·회고·발표: 프로젝트 판단을 전달 가능한 지식으로 만드는 단계

완성 화면만 시연하는 것이 아니라 문제, 결정, 실패, 개선과 검증 증거를 5분 안에 이해할 수 있도록 정리합니다.

이 페이즈에서 하는 일

Codex 대화와 팀의 판단을 정리하고 재현 가능한 실행 방법, 데모, 한계와 다음 단계를 발표합니다.

필수 결과물

CONVERSATION.mdREADME.md5분 발표자료DEMO_SCRIPT.mdRETROSPECTIVE.md

가장 중요한 기준

화려한 화면보다 팀이 어떤 근거로 선택하고 AI의 제안을 어떻게 검토했는지 전달해야 합니다.

학생 수행 순서

  1. 대화 이력을 편집합니다. 모든 채팅을 복사하지 말고 질문, 핵심 제안, 팀의 수용·수정·거절과 이유를 남깁니다.
  2. 재현 방법을 완성합니다. 설치, 실행, 테스트, 데모 계정과 알려진 제한을 README에서 확인합니다.
  3. 5분 발표 흐름을 만듭니다. 문제 40초, 사용자·해결책 50초, 데모 2분, 판단·검증 1분, 회고·다음 단계 30초로 구성합니다.
  4. 실패를 대비한 데모를 준비합니다. 초기화된 데이터, 시연 순서, 예비 화면 캡처와 발표자 역할을 정합니다.
  5. 팀 회고를 작성합니다. 잘한 점, 어려웠던 점, AI 오류, 다시 한다면 바꿀 점과 다음 실험을 구체적으로 적습니다.

발표에서 반드시 보여 줄 것

  • 해결하려는 실제 사용자 문제와 프로젝트 범위
  • 학생 출석부터 선생님 확인까지의 핵심 데모
  • 가장 어려웠던 결정 하나와 선택 근거
  • Codex 제안을 그대로 사용하지 않고 수정하거나 거절한 사례
  • 테스트 증거와 아직 해결하지 못한 한계
  • 다음 버전에서 가장 먼저 개선할 한 가지

완료 체크

  • 5분 이내 발표를 실제로 리허설했다.
  • 네트워크 없이도 설명 가능한 예비 자료가 있다.
  • 모든 팀원이 자신의 기여와 판단을 설명할 수 있다.
  • 실행 방법, 테스트 결과, 한계가 저장소에 남아 있다.

Codex 활용 포인트

CONVERSATION.md와 프로젝트 문서를 바탕으로 5분 발표 초안을 만들어 줘. 기능 목록이 아니라 문제-사용자-핵심 결정-데모-검증 증거-한계-다음 단계 순서로 구성해 줘. 팀이 AI 제안을 수용·수정·거절한 사례를 구분하고, 증거가 없는 성과는 추가하지 마.
