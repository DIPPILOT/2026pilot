코덱스(Codex) 대화 기반 웹사이트 제작 프로젝트

이 수업은 코덱스에 곧바로 “웹사이트 만들어 줘”라고 요청하는 대신, 아이디어 대화부터 Markdown 기획서 작성, 코드 생성, 테스트 및 이력 관리까지의 6단계 정석 프로젝트 프로세스를 완수하는 실습 과정입니다.

학생 프로젝트 진행 방법

  1. 한 페이즈씩 완료하세요. 앞 단계의 산출물이 다음 단계의 입력 자료가 됩니다.
  2. Codex의 결과를 그대로 채택하지 마세요. 사실, 가정, 결정, 미결 질문을 구분하고 팀이 판단한 근거를 남깁니다.
  3. 각 카드의 상세 가이드를 확인하세요. 페이즈 목적, 수행 순서, 필수 결과물, 실무 고려사항과 완료 체크리스트가 제공됩니다.
  4. 완성보다 검증 가능한 과정이 중요합니다. 왜 그렇게 설계했는지 문서와 테스트 증거로 설명할 수 있어야 합니다.

🧰 gstack으로 각 페이즈 진행하기

gstack은 Garry Tan이 공개한 오픈소스 AI 코딩 스킬 모음입니다. 아이디어 검토, 설계 리뷰, 코드 리뷰, QA, 회고 같은 역할을 슬래시 명령으로 불러 쓸 수 있고, Codex CLI에서도 동작합니다. 아래 각 페이즈 카드의 보라색 박스에 해당 단계에서 쓸 gstack 스킬이 정리되어 있습니다.

Think → Plan → Build → Review → Test → Ship → Reflect
# 프로젝트 폴더 안에 설치 (Codex용)
git clone --single-branch --depth 1 https://github.com/garrytan/gstack.git .agents/skills/gstack
cd .agents/skills/gstack && ./setup --host codex
  • 설치에는 Git과 Bun(v1.0 이상)이 필요합니다. Windows는 Node.js도 필요합니다.
  • gstack 스킬의 결과도 Codex 결과와 똑같이 다룹니다. 그대로 채택하지 말고 팀이 판단한 근거를 Markdown 문서와 CONVERSATION.md에 남깁니다.
  • 사용한 gstack 명령과 결과 요약은 매번 CONVERSATION.md에 기록합니다.

🚀 Project Day 6대 핵심 페이즈 (Tasks)

Phase 1

아이디어 구체화 (Idea Definition)

사이트 목적, 사용자 역할(학생/선생님), 핵심 행동을 3문장 이내로 명확히 정리합니다.

핵심 결과물문제·사용자·핵심 행동이 드러나는 프로젝트 정의문

중요 기준팀원 모두가 같은 제품을 상상할 수 있는가?

🧰 gstack 활용 · Think
  • /office-hours 6가지 핵심 질문으로 아이디어의 전제를 점검하고, 누구의 어떤 문제를 푸는지 다시 정리해 디자인 문서를 만듭니다.

💡 결과 디자인 문서를 그대로 쓰지 말고 “문제·사용자·핵심 행동” 3문장 정의문으로 압축합니다. 이 문서가 Phase 2의 입력이 됩니다.

상세 실습과제 가이드 확인
Phase 2

기획 문서화 (Markdown Specs)

SITE_SPEC, USER_FLOWS, DATA_MODEL, IMPLEMENTATION_PLAN, CONVERSATION 문서 팩을 작성합니다.

핵심 결과물서로 모순 없이 연결되는 5개 Markdown 기획 문서

중요 기준개발자가 추가 질문 없이 첫 구현을 시작할 수 있는가?

🧰 gstack 활용 · Plan
  • /plan-ceo-review 범위를 점검합니다. 하루 안에 끝내야 하므로 Hold Scope 또는 Reduction 모드로 꼭 필요한 기능만 남깁니다.
  • /plan-eng-review 데이터 흐름, 예외 상황, 테스트 계획을 확정해 DATA_MODEL·IMPLEMENTATION_PLAN에 반영합니다.
  • /autoplan (선택) CEO·디자인·엔지니어링 리뷰를 한 번에 돌리고 사람이 결정할 항목만 받습니다.

💡 리뷰에서 나온 결정과 보류 항목은 5개 문서 중 어디에 반영했는지 CONVERSATION.md에 남깁니다.

기획서 요약서 작성 가이드
Phase 3

코덱스 기반 웹사이트 구현

코덱스에 문서를 먼저 읽게 한 뒤 website/ 폴더 아래 반응형 웹사이트 코드 생성을 요청합니다.

핵심 결과물실행 가능한 웹사이트와 구현·검증 기록

중요 기준문서의 완료 기준이 코드에 실제 반영됐는가?

🧰 gstack 활용 · Build · Review
  • /freeze 수정 범위를 website/ 폴더로 묶어 기획 문서가 실수로 바뀌지 않게 합니다.
  • /design-consultation (선택) 색상·타이포그래피 등 간단한 디자인 기준을 먼저 정합니다.
  • /review 구현 후 코드를 리뷰해 실제 사용 시 터질 수 있는 버그를 찾습니다.

💡 구현 요청은 기존처럼 “문서 먼저 읽기 → 코드 생성” 순서를 지킵니다. gstack은 그 앞뒤의 범위 제한과 검토에 씁니다.

구현 요청 프롬프트 예시
Phase 4

기능 및 시나리오 테스트

학생 QR 생성/스캔 출석과 선생님 대시보드 실시간 현황 및 예외 방어 처리를 테스트합니다.

핵심 결과물정상·예외 시나리오 테스트 결과와 결함 목록

중요 기준성공 화면뿐 아니라 실패 상황도 안전하게 처리하는가?

🧰 gstack 활용 · Test
  • /qa-only 실제 브라우저로 QR 출석·대시보드 시나리오를 테스트하고 코드는 고치지 않은 채 결함 목록만 받습니다.
  • /investigate 원인이 불분명한 결함은 수정 전에 근본 원인부터 조사합니다.
  • /qa 결함 목록을 확인한 뒤 수정·재검증과 회귀 테스트 생성을 맡깁니다.

💡 Phase 2에서 /plan-eng-review로 만든 테스트 계획을 QA가 이어받습니다. 정상·예외 결과를 표로 정리하세요.

테스트 시나리오 확인
Phase 5

사이트·문서 연쇄 개선

변경 요청을 기획 문서에 먼저 반영(Spec-First)한 뒤 코덱스를 통해 사이트를 개선합니다.

핵심 결과물변경 명세, 영향 분석, 수정 코드와 회귀 테스트

중요 기준변경으로 기존 기능이 깨지지 않았음을 증명했는가?

🧰 gstack 활용 · Plan · Review · Test
  • /plan-eng-review 변경 요청을 반영한 기획 문서를 다시 리뷰해 영향 범위를 분석합니다 (Spec-First).
  • /review 수정된 코드를 리뷰해 기존 기능에 미치는 영향을 확인합니다.
  • /qa 회귀 테스트를 다시 돌려 기존 기능이 깨지지 않았음을 증명합니다.

💡 순서를 지키세요: 문서 수정 → 리뷰 → 코드 수정 → 회귀 테스트. 코드부터 고치면 Spec-First가 아닙니다.

개선 가이드 확인
Phase 6

작업 이력 기록 및 회고 발표

CONVERSATION.md에 프롬프트 및 결정 이력을 기록하고 5분 최종 발표를 진행합니다.

핵심 결과물재현 가능한 작업 기록과 5분 프로젝트 발표

중요 기준무엇을 만들었는지보다 왜 그렇게 판단했는지 설명하는가?

🧰 gstack 활용 · Reflect
  • /document-release 최종 코드에 맞춰 기획 문서와 README를 업데이트해 문서와 사이트를 일치시킵니다.
  • /retro 작업 이력을 바탕으로 잘된 점·아쉬운 점·다음 개선점을 정리해 발표 자료로 씁니다.

💡 발표에서는 각 페이즈에서 어떤 gstack 스킬을 썼고, 그 결과 중 무엇을 채택·거절했는지와 그 이유를 설명합니다.
