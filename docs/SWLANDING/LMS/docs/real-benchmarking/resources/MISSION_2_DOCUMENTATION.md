## 2. 시작 조건 확인하기

다음 세 항목에 모두 답할 수 있을 때 시작합니다.

1. 선택한 사용자는 누구인가?
2. 그 사용자가 완료할 대표 과업은 무엇인가?
3. 어떤 `OBS-###`와 `EXP-###`가 구현의 출발점인가?

답할 수 없다면 [미션 1](MISSION_1_GROWTH_BENCHMARK.md)로 돌아가 관찰 범위를 줄입니다.

## 3. 먼저 근거 추적표 만들기

세 문서 중 하나에 아래 표를 만들고 작업 중 계속 갱신합니다.

| 관찰 | 관찰에서 얻은 원리 | 제품 요구사항 | BM 가설 | 기술 결정 | 상태 |
|---|---|---|---|---|---|
| OBS-001 | 예: 행동 전 신뢰 근거 노출 | PRD-001 | BM-001 | ADR-003 | 초안 |

ID 규칙:

- `OBS-###`: 직접 관찰한 근거
- `PRD-###`: 사용자가 경험해야 하는 제품 요구사항
- `BM-###`: 가치 교환이나 지속 가능성 가설
- `ADR-###`: 구현 방법과 이유를 담은 기술 결정

## 4. 문서 A: 제품 기회 정의

파일: `docs/01-product/OPPORTUNITY.md`

아래 목차를 그대로 복사해 작성합니다.

```markdown
# 제품 기회 정의
## 1. 한 문장 기회
## 2. 대상 사용자와 상황
## 3. 현재 행동과 문제
## 4. 벤치마크에서 발견한 원리
## 5. 새 서비스의 가치 제안
## 6. 대표 사용자 여정
## 7. 제품 요구사항 PRD-###
## 8. MVP 포함 범위
## 9. MVP 제외 범위
## 10. 성공 지표와 검증 방법
## 11. 위험과 미확정 질문
## 12. 관련 근거와 문서 링크
```

### PRD 작성 형식

```markdown
### PRD-001 — [사용자가 얻을 결과]
- 연결 근거: OBS-___, EXP-___
- 사용자 스토리: [사용자]는 [목표]를 위해 [행동]할 수 있어야 한다.
- 수용 기준:
  - [ ] 화면에서 확인 가능한 조건
  - [ ] 실패 시 사용자에게 보이는 피드백
  - [ ] 모바일과 키보드 사용 조건
- 제외 사항:
- 성공 지표:
```

“추천 기능 구현”처럼 해결책만 쓰지 않습니다. 사용자가 얻는 결과와 완료 여부를 확인할 기준을 씁니다.

## 5. 문서 B: 비즈니스 모델 정의

파일: `docs/02-business/BUSINESS_MODEL.md`

```markdown
# 비즈니스 모델 정의
## 1. 모델 한 문장 요약
## 2. 이해관계자와 각자의 목표
## 3. 주고받는 가치
## 4. 획득·활성화·유지·추천·수익 구조
## 5. Business Model Canvas 9개 블록
## 6. BM-### 가설
## 7. 비용과 단위 경제성
## 8. 신뢰·공정성·개인정보 위험
## 9. 검증 순서와 중단 기준
## 10. 관련 근거와 문서 링크
```

Business Model Canvas는 사업이 누구에게 어떤 가치를 어떤 구조로 제공하고 비용과 수익을 어떻게 만드는지 한 페이지에서 연결하는 도구입니다. 처음이라면 [Strategyzer 공식 설명](https://www.strategyzer.com/library/the-business-model-canvas)을 읽습니다.

### BM 가설 작성 형식

```markdown
### BM-001 — [가설 이름]
- 연결 근거: OBS-___, PRD-___
- 지불하거나 기여하는 주체:
- 얻는 가치:
- 서비스가 받는 가치:
- 핵심 지표:
- 검증 방법:
- 성공 기준:
- 실패 시 변경할 내용:
```

수익 모델이 명확하지 않다면 광고나 구독을 억지로 넣지 않습니다. 콘텐츠 생산, 데이터 제공, 재방문, 운영비 절감처럼 서비스가 지속되는 데 필요한 가치도 BM 가설이 될 수 있습니다.

## 6. 문서 C: 개발 기본설계

파일: `docs/03-engineering/BASE_ARCHITECTURE.md`

```markdown
# 개발 기본설계
## 1. 구현 목표와 대표 사용자 흐름

## 3. 시스템 경계와 데이터 흐름
## 4. 기술 스택과 선택 이유
## 5. 폴더와 컴포넌트 구조

## 8. 오류와 빈 상태
```

```markdown
### ADR-001 — [결정 제목]
- 상태: 제안/채택/폐기
- 연결 요구사항: PRD-___, BM-___
- 문제:
- 선택:
- 선택 이유:
- 포기한 대안:
- 예상 부작용:
- 다시 검토할 조건:
```

## 7. MVP 범위 자르기

다음 질문에 `예`라고 답할 수 없는 기능은 미션 3에서 제외합니다.

- 대표 사용자가 한 번의 방문에서 경험할 수 있는가?
- 최우선 성장 가설을 보여 주는가?
- 6~10시간 안에 기본 흐름을 구현하고 테스트할 수 있는가?
- 외부 서비스나 실제 개인정보 없이 데모할 수 있는가?

권장 화면은 1~3개, 핵심 사용자 흐름은 1개입니다. 로그인, 결제, 실시간 채팅, 추천 알고리즘은 목업 데이터로 대체할 수 있습니다.

## 8. 분석 이벤트 정의하기

| 이벤트 | 발생 조건 | 연결 지표 | 포함 데이터 | 금지 데이터 |
|---|---|---|---|---|
| `primary_cta_click` | 핵심 CTA 클릭 | 의도율 | CTA 위치 | 이름, 이메일 |
| `primary_flow_complete` | 대표 과업 완료 | 완료율 | 흐름 버전 | 자유 입력 원문 |

이벤트는 화면 조회보다 사용자 행동을 우선합니다. 이벤트 개념이 낯설면 [Google Analytics 공식 이벤트 설명](https://support.google.com/analytics/answer/9322688)을 참고합니다.

## 9. AI로 세 문서 교차 검토하기

각 문서를 따로 생성시키지 말고 작성 후 모순 검토에 사용합니다.

```text
아래 세 문서는 같은 서비스의 제품·비즈니스·기술 정의다.
새로운 기능이나 사실을 만들지 말고 다음만 찾아줘.

1. OBS 근거가 없는 PRD/BM/ADR
2. 같은 용어를 다르게 사용한 부분
3. 제품 범위와 개발 범위가 충돌하는 부분
4. 측정할 수 없는 성공 기준
5. 개인정보·저작권·보안 위험

결과는 문제 위치, 이유, 최소 수정안 표로 작성해줘.

[세 문서 붙여넣기]
```

AI가 지적한 항목마다 `수정`, `보류`, `기각` 중 하나를 정하고 이유를 남깁니다.

## 11. 제출 전 자기점검

- [ ] 세 문서가 같은 사용자와 대표 과업을 설명한다.
- [ ] 모든 핵심 요구사항에 `OBS-###`가 있다.
- [ ] PRD마다 화면에서 확인 가능한 수용 기준이 있다.
- [ ] BM 가설에 검증 방법과 실패 기준이 있다.
- [ ] ADR에 선택 이유와 포기한 대안이 있다.
- [ ] MVP 포함·제외 범위가 명시되어 있다.
- [ ] 분석 이벤트에 개인정보가 포함되지 않는다.
- [ ] 세 문서가 서로 링크되어 있다.
