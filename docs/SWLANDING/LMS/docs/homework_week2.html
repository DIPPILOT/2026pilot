HW-D06-01. 실시간 비디오 재생기 & 상태 바인딩 UI 구현

🚨 실전 비즈니스 상황 (Production Context)

VidAce 웹 플랫폼에서 4K/FHD 고화질 스트리밍을 제공하는 핵심 비디오 플레이어 UI 컴포넌트를 개발 중입니다. 플레이어는 단순한 재생/일시정지 외에도 다음과 같은 복합 비동기 상태를 하나의 화면에서 처리해야 합니다:

  • 재생 상태 라이프사이클: IDLE → LOADING → PLAYING → BUFFERING → ERROR → ENDED
  • 광고 노출 상태: 프리롤 광고(5초 카운트다운 후 '광고 건너뛰기' 활성화), 미드롤 광고 삽입 시 플레이어 일시정지 및 광고 전용 프로그레스바 전환
  • 시청 통계 및 통신: 1초마다 발생하는 timeupdate 이벤트를 그대로 서버로 전송할 경우 초당 수천 명의 동시 접속으로 인한 서버 폭주 위험 → 5초 간격 쓰로틀링(Throttling) 및 배치 비동기 전송 필수
💡 스스로 생각할 질문 (Self-Reflection Questions)
  • 단순 React useState나 전역 변수로 관리할 때, 광고 재생 상태와 비디오 재생 상태가 뒤엉켜 검은 화면이 발생하는 결함을 어떻게 상태 머신(Finite State Machine)으로 방지할 것인가?
  • 네트워크 지연으로 버퍼링이 3초 이상 지속될 때, 사용자의 이탈을 방지하기 위한 UI 피드백(스켈레톤, 스피너, 저화질 자동 전환 알림)을 어떻게 바인딩할 것인가?
  • 브라우저 탭이 백그라운드로 전환되거나 사용자가 창을 닫을 때(beforeunload) 마지막 시청 시점을 유실 없이 전송하려면 navigator.sendBeacon을 어떻게 연동해야 하는가?

비디오 스트리밍 웹 플레이어 컴포넌트를 작성 중입니다.

DAY 6 • 과제 2 (HW-D06-02)

HW-D06-02. AdBlock 차단 및 네트워크 단절 대응 Fallback UX

🚨 실전 비즈니스 상황 (Production Context)

VidAce 런칭 베타 테스트에서 약 35%의 유저가 uBlock Origin, AdGuard 등의 브라우저 확장 프로그램을 사용 중인 것으로 확인되었습니다. 이로 인해 광고 서버(ad.vidace.com)로의 모든 API 호출이 브라우저 레벨에서 net::ERR_BLOCKED_BY_CLIENT로 강제 중단되었습니다.

// 치명적 장애 현상 발생! AdService.fetchAd() → Error: net::ERR_BLOCKED_BY_CLIENT 결과: Promise.all()이 거부(Reject)되어 본편 동영상 스트림 로더까지 정지됨! 사용자 화면: 검은색 빈 화면(Black Screen)으로 무한 멈춤 현상 발생!

비즈니스 팀 요구: 광고가 차단되었다고 해서 유료 시청자를 잃을 수 없으므로, 광고 로딩 실패 시 3초 이내에 자체 하우스 광고(공익 광고 또는 VidAce 오리지널 티저)로 대체하거나 부드럽게 본편 재생으로 직행해야 합니다.

💡 스스로 생각할 질문 (Self-Reflection Questions)
  • 광고 차단기 감지 라이브러리를 쓰지 않고, 순수 fetch 에러 응답(Failed to fetch)을 다른 네트워크 오류와 어떻게 분기할 것인가?
  • 광고 실패 시 사용자에게 차단기 해제 요청 배너를 띄울 것인가, 아니면 조용히 자체 대체 광고를 띄우고 재생을 계속할 것인가? (비즈니스와 UX의 상충 관계)
  • 동영상 청크 스트리밍 도중 일시적 오프라인 상태가 되었을 때, 플레이어가 크래시되지 않고 지수 백오프(Exponential Backoff)로 자동 재연결을 시도하는 UX는 어떻게 설계해야 하는가?

HW-D07-01. 대용량 동영상 업로드-인코딩 비동기 파이프라인

🚨 실전 비즈니스 상황 (Production Context)

VidAce의 크리에이터 스튜디오에서 2GB~5GB 대용량 4K 비디오 파일을 업로드하는 시스템을 구현해야 합니다. 단일 HTTP POST 요청은 브라우저 타임아웃(30초)이나 네트워크 단절 시 처음부터 다시 올려야 하므로, 5MB 단위 청크(Chunk) 멀티파트 업로드 방식을 채택했습니다.

// 업로드 및 인코딩 동시성 장애 이슈! 1. 크리에이터가 업로드 버튼을 3번 연속 클릭하여 동일한 영상이 3개 생성됨 2. 모바일 와이파이 단절로 Chunk #12가 중복 전송되어 파일이 깨짐 3. 인코딩 완료 웹훅(Webhook)이 네트워크 지연으로 2회 연속 수신되어 인코딩 비용 2배 청구됨!

해결 과제: Idempotency-Key(멱등성 키)를 도입하여 중복 요청을 방지하고, 모든 청크가 수신된 후 SHA-256 체크섬을 검증하여 백그라운드 인코딩 워커로 안전하게 위임하는 백엔드 비즈니스 로직을 구축해야 합니다.

  • 인코딩 상태 전이(UPLOAD_INIT → UPLOADING → COMPLETE → ENCODING → READY / FAILED)에서 이전 상태로 역행하는 레이스 컨디션을 어떻게 방어할 것인가?

클라이언트에서 전송한 Idempotency-Key와 chunk_index를 검증해 중복 수신을 방지하고,
모든 청크가 도착했을 때 최종 파일 조립 후 인코딩 비동기 작업을 큐에 한 번만 등록하는 로직을 작성해줘.

HW-D08-01. 멀티 테넌트 권한(RBAC/ABAC) 매트릭스 및 가드

🚨 실전 비즈니스 상황 (Production Context)

VidAce는 단일 유저 서비스에서 기업형 MCN 채널과 에이전시 광고주를 수용하는 멀티 테넌트 플랫폼으로 확장되었습니다. 이제 한 사용자가 여러 채널에 속할 수 있으며, 채널 내에서도 세부 권한이 나뉩니다:

채널 권한 페르소나 (Creator Team)
• OWNER(채널 소유자): 채널 삭제, 수익 계좌 변경, 멤버 초대, 모든 영상 CRUD 권한
• EDITOR(영상 편집자): 자신이 업로드한 영상 및 담당 영상만 수정/삭제 가능 (타 편집자 영상 삭제 불가)
• ANALYST(데이터 분석가): 시청 통계 및 광고 수익 조회만 가능 (영상 수정/삭제 일체 불가)

보안 취약점 경고: 단순한 Role 체크(user.role === 'EDITOR')만 수행할 경우, 공격자가 요청 바디의 video_id를 타 채널의 동영상 ID로 변조하여 무단 삭제하는 BOLA(Broken Object Level Authorization / IDOR) 공격에 무방비로 노출됩니다.

💡 스스로 생각할 질문 (Self-Reflection Questions)
  • 단순 역할 기반 접근 제어(RBAC)와 리소스 소유권 및 채널 소속을 함께 검증하는 속성 기반 접근 제어(ABAC)를 어떻게 단일 가드 미들웨어로 결합할 것인가?
  • API 요청마다 매번 DB를 조회하여 권한을 확인할 경우 발생하는 DB 병목을 캐싱(Redis, JWT Claim)으로 어떻게 완화하면서도 권한 박탈 시 즉시 반영할 것인가?
  • 클라이언트 UI에서 권한 없는 버튼을 숨기는 것(Frontend Guard)과 백엔드에서 403 Forbidden을 반환하는 것의 보안 책임 분리는 어떻게 이루어져야 하는가?
🤖 AI 질의 예시 (참고용 프롬프트)
⚠️ 참고용 예시입니다: 본인의 백엔드 프레임워크(Express, NestJS, FastAPI 등)에 맞는 미들웨어 형식과 BOLA 방어 시나리오를 구체화하여 질의하세요. 
멀티 테넌트 동영상 플랫폼의 백엔드 권한 인가(Authorization) 가드 미들웨어를 설계해줘.
사용자의 전역 Role뿐만 아니라 특정 채널 내 역할(OWNER, EDITOR, ANALYST)과
동영상 리소스의 소유권(resource.channel_id === request.channel_id)을 함께 검증하여
BOLA(IDOR) 공격을 방어하는 완성된 코드를 작성해줘.
🎯 실제 수행 과제 (Real Mission Tasks)
1
Role-Permission Matrix 정의서 (role_permission_matrix.md) 4대 역할(VIEWER, CREATOR, ADVERTISER, ADMIN) 및 하위 3대 채널 멤버 역할별 15개 핵심 API 엔드포인트에 대한 접근 허용/거부 매트릭스를 작성합니다.
2

HW-D08-02. OAuth2 토큰 탈취 방지 및 세션 보안 Audit

🚨 실전 비즈니스 상황 (Production Context)

VidAce가 Google 및 Kakao 소셜 로그인을 도입한 이후, 정보보호 외부 감사에서 다음과 같은 치명적인 세션 취약점이 보고되었습니다:

[CRITICAL 1] LocalStorage에 JWT Refresh Token 저장: XSS 공격 스크립트 1줄로 유저의 영구 토큰이 해커 C2 서버로 유출될 수 있음.
[CRITICAL 2] Refresh Token 재사용 탐지 부재: 유출된 토큰을 해커가 사용해 새 Access Token을 발급받아도 기존 사용자는 세션 탈취 사실조차 알지 못함.
[HIGH 3] OAuth2 CSRF 방어 미흡: 인가 코드(Auth Code) 교환 시 state 파라미터 검증 누락으로 계정 연동 가로채기 가능.

해결 요구: HttpOnly, Secure, SameSite=Strict 쿠키를 사용하고, Refresh Token이 갱신될 때마다 기존 토큰을 폐기하며, 이미 사용된 토큰이 다시 제출될 경우 침해로 간주하여 해당 계정의 모든 세션을 강제 만료(Family Invalidation)하는 RTR(Refresh Token Rotation) 아키텍처를 구현해야 합니다.

💡 스스로 생각할 질문 (Self-Reflection Questions)
  • Single Page App(SPA)과 백엔드 API 서버가 서로 다른 도메인(api.vidace.com vs www.vidace.com)일 때 SameSite 쿠키와 CORS 설정을 어떻게 해야 쿠키가 유실되지 않는가?
  • 토큰 교체 시점에 모바일 네트워크 지연으로 인해 정상 클라이언트가 직전 토큰을 실수로 2회 연속 보냈을 때 오탐으로 세션이 끊기는 현상을 방지하는 유예 시간(Grace Period 10초) 처리는 어떻게 하는가?
  • 세션 무효화(Revocation List)를 Redis에 저장할 때 토큰의 잔여 만료 시간(TTL)을 일치시켜 메모리 낭비를 줄이는 기법은 무엇인가?
🤖 AI 질의 예시 (참고용 프롬프트)
⚠️ 참고용 예시입니다: 아래 프롬프트를 복사해 제출하면 안 됩니다. 토큰 패밀리 관리와 이상 탐지 메커니즘을 상세히 다루는 독자적 프롬프트를 구성하세요. 
보안이 강화된 JWT Refresh Token Rotation(RTR) 서비스 코드를 구현해줘.
1) HttpOnly/Secure 쿠키를 사용한 토큰 발급
2) 토큰 갱신 시 기존 Refresh Token 무효화 및 새 토큰 패밀리(Family ID) 발급
3) 이미 사용된 폐기 토큰이 재전송되었을 때 침해를 감지하고 해당 유저의 모든 활성 세션을 즉시 무효화하는 로직을 포함해줘.

HW-D09-02. 결제 타임아웃 보상 트랜잭션(Saga) 및 정산 대사

🚨 실전 비즈니스 상황 (Production Context)

대규모 프로모션 데이, PG사 전산망에 순간적인 트래픽 폭주가 발생하여 VidAce 서버에서 PG사 승인 API를 호출한 후 HTTP 504 Gateway Timeout이 발생했습니다. VidAce 서버는 승인 여부를 알지 못해 주문을 '실패' 처리했으나, 실제로는 광고주의 카드에서 500만 원이 정상 결제 승인되는 유령 결제(Ghost Transaction)가 발생했습니다.

상태 구분 VidAce 데이터베이스 PG사 실제 원장
타임아웃 발생 건 주문 상태: PAYMENT_PENDING 또는 FAILED 결제 상태: SUCCESS (카드 승인 완료)
광고주 인지 상태 "결제가 실패했습니다" 화면 표시 휴대폰으로 "5,000,000원 결제 완료" SMS 수신

복구 요구사항: 분산 환경에서 2단계 커밋(2PC)이 불가능하므로, Saga 패턴의 보상 트랜잭션과 5분 주기의 정산 대사 워커(Reconciliation Worker)를 구현하여, 불일치 건을 자동으로 감지하고 결제를 자동 취소하거나 잔액을 안전하게 적립해야 합니다.

  • 자동 대사 배치가 돌기 전에 광고주가 고객센터에 항의하거나 동일 건을 다시 결제하는 것을 방지하기 위해 유저 화면에 어떤 '승인 확인 중' 상태를 보여줄 것인가?
  • PG사와의 네트워크가 완전히 단절되어 취소 API마저 실패할 때, 이를 Dead Letter Queue(DLQ)에 적재하고 운영자 알림(Slack/SMS)을 발송하는 폴백 설계는 어떻게 할 것인가?

    DAY 10 • 과제 2 (HW-D10-02)

    HW-D10-02. 대규모 트래픽 장애 대비 서킷 브레이커 & 무중단 롤백

    🚨 실전 비즈니스 상황 (Production Context)

    런칭 당일 오후 8시, 대형 크리에이터의 독점 신작 영상이 공개되며 순간 동시 접속자가 15만 명으로 폭증했습니다. 이로 인해 AI 개인화 추천 엔진 서버와 타게팅 광고 서버의 응답 시간이 8초 이상으로 치솟았고, 백엔드 API 스레드 풀이 고갈되며 핵심 비디오 스트리밍 API까지 연쇄 다운(Cascading Failure)되는 블랙아웃 위기에 직면했습니다.

    // 연쇄 장애 아키텍처 결함! 동영상 상세 페이지 호출 → AdService.getAd() 8초 대기 → RecommendationService 8초 대기 결과: 동영상 재생 URL을 반환하는 API 스레드가 모두 Timeout 대기 상태로 고갈되어 유저들이 동영상 자체를 재생하지 못하는 전면 서비스 마비 사태 발생!

    운영 복구 요구: 서브 시스템(광고/추천)의 오류율이 50%를 넘거나 응답이 1초를 초과하면 즉시 서킷 브레이커(Circuit Breaker)를 오픈(Open)하여 광고 호출을 차단하고 기본 캐시 영상으로 우아한 기능 저하(Graceful Degradation)를 수행해야 합니다. 또한 신규 버전 버그 발견 시 1분 이내에 DB 손실 없이 이전 버전으로 복귀하는 무중단 롤백 런북이 필요합니다.

    💡 스스로 생각할 질문 (Self-Reflection Questions)
    • 서킷 브레이커의 3가지 상태(Closed, Open, Half-Open)에서 복구 상태(Half-Open)로 전환하여 트래픽을 조심스럽게 흘려보내는 시험 요청 비율은 어떻게 설정할 것인가?
    • 데이터베이스 스키마 마이그레이션(예: 컬럼 삭제 또는 변경)이 포함된 배포 버전을 롤백할 때, 구버전 앱이 깨지지 않도록 하위 호환성을 유지하는 Expand/Contract(기둥 기법) 배포 전략은 무엇인가?
    • 런칭 당일 운영팀이 패닉에 빠지지 않고 장애 3분 내에 롤백을 단행할 수 있는 자동화된 Health Check 프로브 기준은 어떻게 수립해야 하는가?
    🤖 AI 질의 예시 (참고용 프롬프트)
    ⚠️ 참고용 예시입니다: 아래 프롬프트를 복사하지 말고, 본인의 아키텍처 스택과 서킷 브레이커 임계치(Failure Threshold)를 반영하여 구체적으로 질문하세요. 
    대규모 트래픽 폭주 시 외부 광고/추천 API 장애가 메인 비디오 스트리밍으로 전파되는 것을 막는
서킷 브레이커(Closed, Open, Half-Open) 미들웨어 코드를 작성해줘.
1초 내 미응답 시 즉시 기본 캐시 데이터를 반환하는 Fallback 로직과,
카나리 배포 실패 시 1분 내 무중단 롤백을 수행하는 SRE 운영 런북을 작성해줘.
    🎯 실제 수행 과제 (Real Mission Tasks)

    서킷 브레이커 & 격리 아키텍처 설계서 (circuit_breaker_architecture.md) 장애 전파 차단 구조, 서킷 상태 머신(Closed → Open → Half-Open), 실패율 임계치 및 Fallback 기본값 정책을 기술합니다.
