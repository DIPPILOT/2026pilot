# 전체 검증 전략

## 1. 목적

모바일 고객 주문과 PC 관리자 기능이 계획 문서, 디자인 콘셉트, Google Sheets 메뉴 데이터에 맞게 구현되었는지 확인합니다. 정상 흐름뿐 아니라 품절, 네트워크 단절, 결제 실패, 동시 변경과 같은 예외 상황까지 검증합니다.

## 2. 검증 범위

### 포함

- 고객 모바일 주문 8개 화면
- 관리자 PC 화면 8개 영역
- 메뉴·옵션·주문 상태 공통 정책
- 고객과 관리자 간 실시간 상태 동기화
- Google Sheets 메뉴 데이터와 화면 데이터의 일치
- 반응형 레이아웃, 접근성, 시각적 일관성
- 브라우저 저장 데이터 초기화와 복구

### 제외

- 실제 카드 승인과 실제 간편결제
- 실제 POS, 영수증 프린터, 주방 디스플레이 연동
- 실제 회원, 쿠폰, 포인트, 배달 주문
- 운영 서버의 부하·보안 침투 테스트

제외 항목은 기능이 추가되는 시점에 별도 검증 범위로 편입합니다.

## 3. 검증 환경

### 로컬 실행

```bash
python3 -m http.server 8000 --directory service-implementation
```

- 통합 화면: `http://127.0.0.1:8000/`
- 고객 화면: `http://127.0.0.1:8000/customer/`
- 관리자 화면: `http://127.0.0.1:8000/admin/`

### 브라우저 기준

| 구분 | 최소 검증 환경 |
|---|---|
| 모바일 | Chrome 기반 브라우저 360×800, 390×844, 430×932 |
| 모바일 보조 | Safari 계열 브라우저 또는 WebKit 호환 환경 |
| PC 관리자 | Chrome 기반 브라우저 1280×720, 1440×900 |
| 확대 | 200% 확대 상태에서 주요 기능 사용 가능 여부 |
| 키보드 | 마우스 없이 Tab, Shift+Tab, Enter, Space, Escape 사용 |

## 4. 검증 단계

### 단계 1: 정적 검사

- JavaScript 문법 검사
- 깨진 로컬 파일 경로 확인
- HTML의 중복 ID와 누락된 레이블 확인
- 기획 문서와 구현 화면 목록 비교

### 단계 2: 데이터 검사

- 시트 헤더와 데이터 타입 확인
- 메뉴 ID 중복 확인
- 분류, 가격, 판매 상태, 표시 순서 검증
- `menu-data.js`와 시트 값 비교
- 앱 초기 상태에 메뉴 11개가 로드되는지 확인

### 단계 3: 기능 검사

- 고객 정상 주문 흐름
- 관리자 주문 처리 흐름
- 고객·관리자 실시간 동기화
- 예외 상태와 복구
- 새로고침 및 브라우저 저장 동작

### 단계 4: 디자인 검사

- 디자인 토큰과 화면 스타일 비교
- 모바일·PC 해상도별 레이아웃 확인
- 상태, 오류, 품절, 선택 표시의 일관성 확인
- 키보드·화면 읽기 도구 기준 접근성 확인

### 단계 5: 회귀 검사

- 수정된 기능의 직접 재검증
- 연관된 장바구니, 가격, 주문 상태, 관리자 통계 재검증
- 신규 메뉴와 기존 주문 데이터의 호환성 확인

## 5. 시작 조건

- 검증 대상 파일이 저장되어 있어야 합니다.
- 로컬 서버가 응답해야 합니다.
- 테스트할 변경 내용이 정리되어 있어야 합니다.
- Google Sheets 메뉴 범위가 읽을 수 있는 상태여야 합니다.
- 테스트 데이터 초기화 방법이 확인되어야 합니다.

## 6. 종료 조건

- 모든 P0·P1 테스트가 PASS 상태여야 합니다.
- 심각도 Critical 또는 High 결함이 없어야 합니다.
- Medium 결함은 해결 일정과 영향 범위가 기록되어야 합니다.
- 고객 정상 주문과 관리자 처리 흐름이 각각 한 번 이상 완주되어야 합니다.
- 모바일 3개 너비와 PC 2개 너비에서 치명적인 레이아웃 문제가 없어야 합니다.
- 최종 보고서에 실행 환경, 결과, 결함, 잔여 위험이 기록되어야 합니다.

## 7. 우선순위

| 우선순위 | 기준 | 예시 |
|---|---|---|
| P0 | 서비스 핵심 흐름, 매번 검증 | 주문, 결제 결과, 주문 접수, 품절 동기화 |
| P1 | 주요 기능과 복구 흐름 | 옵션 검증, 취소, 필터, 저장 실패 복구 |
| P2 | 보조 기능과 편의성 | 다운로드, 출력 모달, 세부 애니메이션 |

## 8. 결함 심각도

| 심각도 | 기준 | 예시 |
|---|---|---|
| Critical | 주문·결제 데이터 손실, 중복 결제, 전체 사용 불가 | 결제 버튼 중복 실행, 주문 생성 실패 |
| High | 핵심 기능 사용 불가, 우회 방법 없음 | 장바구니 담기 불가, 주문 접수 불가 |
| Medium | 일부 기능 오류, 우회 가능 | 특정 필터 오류, 일부 화면 겹침 |
| Low | 문구·정렬·미세한 시각 문제 | 오탈자, 작은 간격 불일치 |

## 9. 증거 수집 규칙

각 실행 기록에 다음 정보를 남깁니다.

- 테스트 ID와 실행 시각
- 실행 환경과 화면 크기
- 입력 데이터
- 실제 결과와 기대 결과
- PASS, FAIL, BLOCKED 상태
- 실패 시 스크린샷 또는 콘솔 오류
- 재현 빈도
- 관련 기획 문서와 구현 파일
- 수정 버전과 재검증 결과

## 10. 변경 유형별 회귀 범위

| 변경 유형 | 반드시 다시 확인할 범위 |
|---|---|
| 메뉴·가격 변경 | 목록, 상세, 장바구니, 주문 확인, 결제 금액, 관리자 메뉴 |
| 옵션 변경 | 필수 선택, 추가 금액, 장바구니 수정, 품절 옵션 |
| 주문 상태 변경 | 관리자 상태 변경, 고객 상태 화면, 대시보드 건수 |
| 디자인 토큰 변경 | 고객 8화면, 관리자 주요 화면, 상태색, 대비 |
| 저장소 버전 변경 | 초기화, 기존 캐시 분리, 고객·관리자 동기화 |
| 시트 동기화 변경 | 행 수, ID, 데이터 타입, 신규 메뉴 상세, 품절 메뉴 |
