# 미션 4 — 설계와 서비스를 증거로 검증하기

## 목표

설계 문서의 품질과 실행 서비스의 품질을 같은 것으로 취급하지 않습니다. 각각 계획, 실행, 증거, 판정을 남깁니다.

## VALIDATION_PLAN.md

| 항목 | 내용 |
|---|---|
| 검증 목적 | 무엇을 통과 또는 실패로 판단할 것인가 |
| 범위 | 포함 화면·기능·문서와 제외 범위 |
| 환경 | 브라우저, 화면 너비, 데이터 버전 |
| 역할 | 실행자, 기록자, 수정 담당 |
| 일정 | 1차 검증, 수정, 재검증 |
| 증거 | 화면, 로그, 테스트 결과, 파일 위치 |
| 종료 기준 | 치명 0건, 높음 0건 등 |

## DESIGN_VALIDATION.md

설계 검증은 다음을 확인합니다.

- PROJECT_BRIEF와 화면 명세의 사용자·범위 일치
- 고객·관리자 용어, 상태, ID의 일관성
- 메뉴·주문 데이터 필드의 완전성
- 화면 행동과 API 계약의 연결
- 요구사항별 수용 기준과 TEST ID
- 권한, 개인정보, 저작권, 실패 조건
- 결정의 담당자, 근거, 재검토일

결과는 통과, 실패, 미검증 중 하나로 판정하고 증거 위치를 기록합니다.

## SERVICE_VALIDATION.md

### 필수 환경

- 모바일: 360 × 800
- PC: 1280 × 800
- 새로고침 전후
- 가상 메뉴 정상 데이터와 품절·빈 데이터
- 네트워크 또는 저장 실패를 재현할 수 있는 환경

### 필수 시나리오

1. 고객이 샌드위치와 음료를 선택해 주문을 완료한다.
2. 관리자가 새 주문을 확인하고 준비·완료로 변경한다.
3. 고객 화면에서 주문 상태를 확인한다.
4. 품절 메뉴를 주문하려 할 때 이유와 대안을 본다.
5. 빈 장바구니로 주문할 수 없다.
6. 저장 실패 후 입력이 사라지지 않고 재시도할 수 있다.
7. 메뉴 가격, 옵션 추가 금액, 수량, 합계가 맞다.
8. 키보드로 주요 흐름을 수행하고 레이블을 이해할 수 있다.

## 심각도

- 치명: 핵심 흐름 진행 불가, 데이터 손상, 보안·개인정보 위험
- 높음: 주요 기능 오작동 또는 잘못된 주문·합계·상태
- 보통: 우회 가능하지만 혼란이나 접근성 문제 발생
- 낮음: 문구, 간격, 경미한 시각 문제

1. Codex가 가장 잘 구조화한 부분은 무엇인가?

4. 학생이 직접 바꾼 결정 중 가장 중요한 것은 무엇인가?
5. 다음 프로젝트에서 가장 먼저 확인할 질문은 무엇인가?
6. 아직 검증하지 못한 위험은 무엇인가?

## 통과 게이트

- 설계 검증과 서비스 검증 보고서가 분리되어 있다.
- 모든 핵심 요구사항에 통과·실패·미검증 판정이 있다.
- 발견 결함에 재현 순서와 증거가 있다.
- 치명·높음 결함은 수정 후 재검증되었다.
- AI와 사람의 판단 차이를 구체적인 ID로 설명한다.
