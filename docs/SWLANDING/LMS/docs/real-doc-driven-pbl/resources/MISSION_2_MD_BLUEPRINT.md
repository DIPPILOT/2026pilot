# 미션 2 — 구현 가능한 Markdown 명세 패키지 만들기

## 목표

Antigravity IDE가 임의로 기능을 추측하지 않도록 화면, 데이터, API, 분석, 검증을 하나의 추적 가능한 계약으로 만듭니다.

## 필수 문서

### CUSTOMER_ORDER.md

- 모바일 기준 너비: 360px 우선
- 시작, 메뉴 탐색, 상세, 옵션, 장바구니, 주문 완료
- 로딩, 빈 결과, 품절, 잘못된 옵션, 저장 실패, 복구 상태
- 화면마다 목적, 표시 정보, 행동, 다음 상태, 수용 기준
- 키보드와 스크린리더 레이블의 기본 기준

### ADMIN_CONSOLE.md

- PC 기준 너비: 1280px 우선
- 오늘의 주문 요약, 주문 목록·검색·필터
- 주문 상세, 접수·준비·완료·취소 상태 변경
- 메뉴 판매 여부와 재고 확인
- 역할과 권한, 실수 방지 확인 단계
- 고객 화면과 공유하는 주문·메뉴 상태

### DESIGN_CONCEPT.md

- 핵심 인상: 신선함, 선택의 즐거움, 빠른 이해
- 색상, 타이포그래피, 간격, 카드, 버튼, 상태 색
- 주문 단계 표시와 엄지손가락 접근 영역
- 관리자 화면의 정보 밀도와 시각적 우선순위
- 레퍼런스에서 가져올 원리와 복제하지 않을 자산
- 모바일·태블릿·PC 반응형 규칙

### MENU_DATA.md

가상의 메뉴를 10개 이상 만듭니다.

| 필드 | 설명 | 예 |
|---|---|---|
| menu_id | 불변 ID | SW-001 |
| category | 샌드위치 또는 음료 | sandwich |
| name | 메뉴명 | 그린 치킨 샌드 |
| description | 짧은 설명 | 채소와 구운 닭가슴살 |
| base_price | 기본 가격 | 7900 |
| options | 빵·치즈·소스·사이즈 | 배열 |
| stock | 현재 수량 | 12 |
| is_available | 판매 가능 | true |
| image_alt | 이미지 대체 텍스트 | 샌드위치 단면 |

시트 필드와 앱 필드가 다르면 매핑표를 추가합니다.

### service-analysis/ANALYSIS_DEFINITION.md

- EVT ID, 발생 화면, 발생 조건, 속성, 지표, 보관 기간
- 예: menu_viewed, option_selected, cart_added, order_completed
- 이름, 전화번호, 주소, 결제 정보 원문은 수집하지 않는다.
- 이벤트 중복, 누락, 순서 역전 검증 방법을 포함한다.

### service-analysis/ANALYTICS_API_DEFINITION.md

- 분석 이벤트 수집 API와 지표 조회 API를 분리한다.
- 요청·응답, 권한, 오류, 멱등성, 데이터 기준 시각을 정의한다.
- 분석 정의와 API가 같은 지표 계산식을 사용하도록 연결한다.

### service-planning/API_CONTRACT.md

각 API에 다음을 정의합니다.

- API ID와 목적
- 메서드와 경로
- 요청 필드와 유효성
- 성공 응답
- 오류 코드와 사용자 대응
- 권한
- 상태 전이
- 연결 요구사항과 테스트 ID

## 문서 감사 질문

1. 같은 메뉴·주문 상태를 서로 다른 이름으로 쓰고 있지 않은가?
2. 화면에는 있지만 데이터나 API가 없는 행동이 있는가?
3. 테스트할 수 없는 “편리하다”, “빠르다” 같은 기준이 있는가?
4. 모바일 고객의 변경이 관리자에 어떻게 보이는가?
5. 실제 개인정보·결제·저작권 위험이 들어갔는가?

## 통과 게이트

- 고객과 관리자 문서에 정상·빈·오류·복구 상태가 있다.
- 메뉴 10개 이상과 옵션·재고가 있다.
- 디자인은 원리를 설명하고 원본 자산을 복제하지 않는다.
- 분석 이벤트에 개인정보가 없다.
- API 오류와 상태 전이가 정의되어 있다.
- 핵심 요구사항이 화면, 데이터, API, 테스트까지 연결된다.
