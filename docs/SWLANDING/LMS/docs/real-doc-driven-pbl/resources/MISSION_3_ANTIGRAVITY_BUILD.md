# 미션 3 — Antigravity IDE에서 MD 계약대로 구현하기

## 목표

service-planning의 승인된 문서를 유일한 구현 계약으로 사용해 모바일 고객 주문과 PC 관리자 화면을 작동하게 만듭니다.

## 시작 전 점검

- service-planning 문서가 미션 2 통과 상태인지 확인한다.
- service-implementation/README.md에 실행, 빌드, 테스트 명령을 기록한다.
- 기술 스택과 버전을 기록한다.
- 실제 결제, 로그인, 개인정보 저장은 구현 범위에서 제외한다.
- 가상 데이터로 전체 흐름을 재현할 수 있게 한다.

## Antigravity 작업 요청 규칙

한 번에 요구사항 ID 하나를 요청합니다.

```text
service-planning의 승인된 MD만 구현 근거로 사용해줘.
이번 작업 범위는 REQ-___ 하나다.
먼저 관련 파일과 불명확한 점을 보고하고 승인되지 않은 기능은 만들지 마.
구현 후 변경 파일, 실행 방법, 수용 기준별 확인 결과를 요약해줘.
```

## 구현 순서

### 사이클 1 — 고객 정상 흐름

1. 메뉴 목록과 분류
2. 메뉴 상세와 옵션
3. 장바구니 수량·합계
4. 주문 확인과 완료 피드백

### 사이클 2 — 관리자 정상 흐름

1. 주문 요약과 목록
2. 주문 상세
3. 접수·준비·완료 상태 변경
4. 고객 주문 상태와의 데이터 정합성

### 사이클 3 — 실패와 복구

1. 품절 메뉴
2. 빈 장바구니
3. 잘못된 옵션
4. 데이터 저장 실패
5. 빈 검색 결과
6. 재시도와 이전 상태 보존

## AI_WORK_LOG.md 형식

| AI ID | 연결 요구사항 | 요청 | 받은 제안 | 실행 결과 | 사람의 수정 | 수용·반려 이유 |
|---|---|---|---|---|---|---|
| AI-001 | REQ-004 | 장바구니 합계 구현 | 가격 합산 함수 | TEST-006 통과 | 음수 수량 방지 추가 | 수정 후 채택 |

최소 5건을 기록하고, 실패하거나 반려한 사례를 2건 이상 포함합니다.

## 구현 중 명세 변경

구현이 문서와 달라져야 한다면 다음 순서를 지킵니다.

1. 차이와 이유를 DECISION_LOG에 기록한다.
2. 영향받는 요구사항, 화면, 데이터, API, 테스트를 찾는다.
3. service-planning 원본을 수정한다.
4. 학생 또는 팀이 변경을 승인한다.
5. 코드를 수정하고 재검증한다.

## 필수 품질 확인

- 360px 모바일에서 가로 스크롤 없이 주문 가능
- 1280px PC에서 관리자 핵심 정보가 한눈에 구분됨
- 키보드로 주요 동작 수행 가능
- 입력 레이블과 버튼 이름이 명확함
- 로딩·빈·오류·성공 피드백 존재
- 메뉴 가격, 옵션, 합계, 주문 상태가 일관됨
- lint, build, 핵심 테스트 통과

모바일 고객 대표 흐름과 PC 관리자 대표 흐름이 실제로 실행되고, 실패 상태가 복구 가능하며, 구현·테스트가 요구사항 ID에 연결되어야 합니다.
