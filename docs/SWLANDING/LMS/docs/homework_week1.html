DAY 1 · HW-D01-02 · 50점

🔥 조회수와 광고 비용은 누구 책임인가

📌 비즈니스 시나리오

VidAce 데이터팀에서 충격적인 보고서를 냈습니다. 광고 노출 이벤트가 실제 노출보다 2.3배 더 많이 기록되고 있으며 월말 광고비가 과다 청구되고 있습니다. 어느 팀도 "우리 책임이 아니다"라고 주장하고 있습니다.

  • 🔴 Viewer가 재생 버튼을 눌렀지만 3초 만에 닫음 → 조회수로 집계되었는가?
  • 🔴 광고가 2번 호출되었지만 Viewer는 1번만 봄 → 과금 기준은?
  • 🔴 네트워크 오류로 재생 신호가 서버에 2번 전달됨 → 이중 기록 방지 책임은?
  • 🔴 30초 광고를 25초 보다가 앱 종료 → 광고 완주로 처리? 부분 처리?
🧠 스스로 생각해볼 질문들
  • 이벤트와 사실의 구분: "재생 버튼 클릭"과 "실제 시청 시작"은 같은 사건인가? 어떤 기준으로 구분할 수 있는가?
  • 소유권의 의미: 어떤 데이터가 어느 팀의 DB에 저장되어야 하는가? 같은 데이터를 두 팀이 각자 저장하면 무슨 문제가 생기는가?
  • 이중 처리 방지: 같은 이벤트가 두 번 들어왔을 때 "첫 번째를 사용"하는 전략과 "마지막을 사용"하는 전략의 차이는?
  • 청구 책임: Advertiser에게 광고비를 청구하는 주체는 누구여야 하는가? 과금 이벤트 기록과 청구는 같은 Domain에서 처리해야 하는가?
💡 예시 프롬프트 (참고용 — 그대로 사용하지 마세요)
Domain 분석은 이벤트 목록과 시나리오를 본인이 먼저 분류한 뒤 AI에게 검토를 요청하세요.
예시 프롬프트 — HW-D01-02
[역할] 당신은 Domain-Driven Design 전문가입니다.
[컨텍스트] 영상 광고 플랫폼에서 재생 요청, 실제 시청, 광고 노출, 과금 발생이
서로 다른 이벤트이며, 현재 이중 기록 문제가 발생하고 있습니다.
[분석 대상 도메인] Video, Playback, Ad, Impression, Charge, User
[요청]
1) 각 Domain의 주 책임(Primary Responsibility)과 원본 데이터 소유권을 한 줄로 정의하라
2) "재생 요청 → 시청 시작 → 광고 노출 → 과금"의 책임 분리 방식을 2가지 대안으로 비교하라
3) 이중 이벤트 수신 시 처리 정책(Idempotency Key 방식 등)을 제안하라
🎯 실제 과제 — 직접 수행하세요
1
이벤트 유형 분류표 작성
최소 8개 이벤트 유형을 정의하고 각각 "집계 대상인가 / 과금 대상인가 / 이중 처리 위험이 있는가"를 Yes/No와 이유로 구분하세요.
2
Domain 책임 맵 (domain_map.md)
최소 5개 Domain을 정의하고 각각 ①주 책임 정의, ②소유 데이터 목록, ③공유해야 할 이벤트/데이터, ④절대 직접 쓰지 말아야 할 데이터를 명시하세요.

🗣️ Participant D: "제출 완료 버튼을 눌렀는데 아무 반응이 없었어요. 다시 눌렀더니 '이미 제출된 캠페인입니다'라고 나와요."
🗣️ Participant E: "광고비가 얼마나 쓰였는지 보고 싶은데 만든 후에 확인할 방법을 모르겠어요."
🧠 스스로 생각해볼 질문들
  • 비판의 방향: 각 피드백이 디자인의 어떤 원칙을 위반하고 있는가? Nielsen의 10가지 휴리스틱 중 어떤 것과 관련되는가?
  • 기술 vs UX 문제: Participant B의 문제(진행 데이터 소실)는 UX 문제인가, 기술 구현 문제인가? 해결하려면 무엇을 바꿔야 하는가?
  • 피드백의 진짜 문제: Participant A는 "심의 중"이라는 단어를 몰랐다고 했지만, 실제 문제는 단어인가 아니면 상태를 설명하는 방식 자체인가?
  • 개선의 검증: 개선된 화면이 실제로 더 좋은지 어떻게 확인할 수 있는가? 어떤 측정 기준을 사용해야 하는가?
💡 예시 프롬프트 (참고용 — 그대로 사용하지 마세요)
비판은 구체적이어야 합니다. 먼저 피드백 5개를 읽고 각각의 근본 원인(Root Cause)을 스스로 찾아보세요. 그 후 AI와 대화하세요.
예시 프롬프트 — HW-D05-02
[역할] 당신은 UX 감사자(Auditor)입니다.
[컨텍스트] 캠페인 생성 화면에 대한 사용성 테스트에서 5가지 피드백이 수집되었습니다.
[분석 대상 피드백] (피드백 5개 목록 붙여넣기)
[요청]
1) 각 피드백의 근본 원인(UX 원칙 위반 또는 기술 구현 문제)을 분류하라
2) 각 피드백에 대한 개선 방안을 Before/After 형식으로 제시하라
3) 개선 결과를 검증할 사용성 테스트 기준 3가지를 작성하라
🎯 실제 과제 — 직접 수행하세요
1
피드백 5개 근본 원인 분석
각 피드백에 대해 ①문제가 발생한 화면/컴포넌트, ②위반된 UX 원칙(Nielsen 휴리스틱 등 근거), ③문제의 심각도(1-5점, 비즈니스 영향 기준), ④기술적/UX적 원인 분류를 작성하세요.
2
개선 전/후(Before/After) 화면 명세
5개 피드백 각각에 대해 개선된 화면 설계를 Before/After 형식으로 작성하세요. 컴포넌트 구조, 사용자 흐름, 정보 계층이 어떻게 달라졌는지 UX 원칙에 근거하여 설명하세요.
3
사용성 재검증 기준 3개 작성
개선된 화면이 실제로 더 좋아졌는지 확인하는 측정 가능한 기준 3개를 작성하세요. 각 기준은 측정 방법(관찰, 설문, 완료율 등)과 성공 기준(숫자)을 포함하세요.
4
설계 의사결정 기록
5가지 피드백 중 ①수용한 것, ②부분 수용한 것(비수용 이유), ③수용하지 않은 것(반박 근거)을 구분하여 기록하세요. 수용하지 않은 경우 재검증 조건도 함께 작성하세요.
